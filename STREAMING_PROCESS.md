# Streaming Process on the Two Camera Boards

How the S3-N16R8-OV5640 and S3-N8R8-OV3660 camera boards capture, transfer, and
render a live MJPEG stream, plus the hardware details (pins, clocks, PLLs) that
make it work. Both projects are byte-identical in architecture and differ only
in the sensor, the flash size, and the antenna.

## 1. Two boards, one design

| | S3-N16R8-OV5640 | S3-N8R8-OV3660 |
|---|---|---|
| Project | `s3-n16r8-ov5640/camera_stream` | `s3-n8r8-ov3660/camera_stream` |
| SoC | ESP32-S3 (dual-core 240 MHz) | ESP32-S3 (dual-core 240 MHz) |
| Flash / PSRAM | 16 MB / 8 MB octal | 8 MB / 8 MB octal |
| Sensor | OV5640 (5 MP, PID 0x5640) | OV3660 (3 MP, PID 0x3660) |
| Antenna | PCB (printed on board) | inserted (external) |
| XCLK | 20 MHz | 20 MHz |
| Frame buffer | fixed 2 MB x2 (custom) | auto w*h/5 x2 |
| QVGA stream (measured) | ~22.2 FPS, max gap 90 ms | ~27.7 FPS, max gap 70 ms |

Everything described below applies to both; per-sensor differences are called
out where they matter.

## 2. Hardware details

### 2.1 Pin map (ESP32S3-EYE pinout, identical on both boards)

All pin assignments are in `main/main.c` (`CAM_PIN_*` defines).

| Signal | GPIO | Role |
|--------|------|------|
| XCLK   | 15   | Master clock **into** the sensor (generated by the SoC) |
| SIOD   | 4    | SCCB serial data (the camera's I2C) |
| SIOC   | 5    | SCCB serial clock (the camera's I2C) |
| D7     | 16   | DVP data Y9 (MSB) |
| D6     | 17   | DVP data Y8 |
| D5     | 18   | DVP data Y7 |
| D4     | 12   | DVP data Y6 |
| D3     | 10   | DVP data Y5 |
| D2     | 8    | DVP data Y4 |
| D1     | 9    | DVP data Y3 |
| D0     | 11   | DVP data Y2 (LSB) |
| VSYNC  | 6    | Vertical sync (frame start) |
| HREF   | 7    | Horizontal reference (line active) |
| PCLK   | 13   | Pixel clock (sensor shifts 1 byte per PCLK edge) |
| PWDN   | -1   | Not wired (power-down held low by module) |
| RESET  | -1   | Not wired |

The sensor is a **DVP (parallel) camera**: 8 data lines + PCLK + VSYNC + HREF.
The ESP32-S3 **LCD_CAM peripheral** captures those pins and feeds the bytes to a
DMA chain. There is no CSI MIPI bus on these boards.

SIOD/SIOC are the **SCCB/I2C register bus** (GPIO4/5, hardware I2C port 1) —
they carry sensor configuration, never pixels. See §8 for the full IIC/SCCB
behavior.

### 2.2 XCLK generation: the LCD_CAM module, not LEDC

On the original ESP32 the XCLK was produced by a PWM (LEDC) timer
(`config.ledc_timer` / `config.ledc_channel`). On the **ESP32-S3 the LCD_CAM
module itself generates XCLK** — `CAMERA_ENABLE_OUT_CLOCK()` in
`esp_camera.c` is a compile-time no-op for `CONFIG_IDF_TARGET_ESP32S3`
(`driver/esp_camera.c:100`).

`target/esp32s3/ll_cam.c` does the actual clocking:

```c
LCD_CAM.cam_ctrl.cam_clkm_div_num = 160000000 / config->xclk_freq_hz; // 160 MHz / 20 MHz = 8
...
gpio_matrix_out(config->pin_xclk, CAM_CLK_IDX, false, false);          // route to GPIO15
```

So XCLK = 160 MHz / 8 = **20 MHz** square wave on GPIO15. The `ledc_timer` /
`ledc_channel` fields are accepted but unused on the S3. 20 MHz is the value
from the vendor kit (`Sketch_07.1_CameraWebServer.ino`) and is **not
overclocked** (the driver's PLL tables are tuned around it).

### 2.3 Sensor-side clock scaling (PLLs)

The sensor takes the 20 MHz XCLK and synthesizes its internal clocks
(SYSCLK drives the image pipeline + JPEG encoder; PCLK drives the DVP output).
The driver picks registers per format/frame size and prints the result.

**OV5640 — JPEG mode, QVGA..XGA** (`sensors/ov5640.c:434`):
`set_pll(sys_mul=180, sys_div=4, pre_div=2, pclk_root_div=2, pclk_div=4)`

```
XVCLK 20 MHz -> REFIN 10 MHz -> VCO 1800 MHz -> PLL_CLK 180 MHz
SYSCLK = PLL_CLK / 4         = 45 MHz   (JPEG encoder clock)
PCLK   = PLL_CLK/root/div    = 11.25 MHz (DVP pixel clock)
```
(`sys_mul` is 160 below QVGA / at 16 MHz XCLK, and 200 at XGA+; the PCLK
stays ~10-11 MHz. This PCLK is why QVGA tops out at ~22 FPS.)

**OV3660 — JPEG mode, below QXGA** (`sensors/ov3660.c:358`):
`set_pll(mul=30, sys_div=1, pre_div=3, seld5=0, pclk_div=10)`

```
XVCLK 20 MHz -> VCO 200 MHz -> PLLCLK 200 MHz
SYSCLK = PLLCLK / 4 = 50 MHz   (higher JPEG-encode clock than OV5640)
PCLK   = PLLCLK / 2 / 10 = 10 MHz
```
(QXGA or 16 MHz XCLK drops to `mul=24, pclk_div=8` -> 40 MHz SYSCLK.)

The higher SYSCLK (50 vs 45 MHz) is the main reason the OV3660 streams faster
even though its PCLK is *lower*: the in-sensor JPEG encoder is the bottleneck,
and it is clocked by SYSCLK, not PCLK.

### 2.4 Frame buffers

- **OV5640**: `sdkconfig.defaults` sets `CONFIG_CAMERA_JPEG_MODE_FRAME_SIZE=2097152`,
  so each frame buffer is a fixed **2 MB** PSRAM allocation (the driver's
  default `w*h/5` overflows at UXGA+ for quality 12). `fb_count = 2` -> 2 x 2 MB.
- **OV3660**: auto buffer (`w*h/5`), `fb_count = 2`.

## 3. How a frame is captured

1. **`esp_camera_init(&s_camera_config)`** probes the SCCB bus for a known
   sensor (address 0x3C), detects OV5640/OV3660 by PID, programs the PLL and
   frame size, and allocates the PSRAM frame buffers.
2. **`cam_task()`** (`driver/cam_hal.c`) is a FreeRTOS task that waits on an
   event queue fed by LCD_CAM interrupts. On **VSYNC** it starts capturing; the
   LCD_CAM+DMA stream bytes (YUV/RGB or already-JPEG) into a ping-pong DMA
   double-buffer in PSRAM, then `cam_task` assembles them into a frame buffer.
3. **On-board JPEG**: both sensors have an **internal JPEG encoder**. In
   `PIXFORMAT_JPEG` the CPU never sees raw pixels — the sensor's encoder
   (clocked by SYSCLK) produces a complete JPEG bitstream that is DMA'd out.
   The CPU only copies bytes. (In `PIXFORMAT_RGB565` raw 2 bytes/pixel come
   out and the app compresses later — see §4.)
4. When a full frame lands, it is queued on `frame_buffer_queue`. With
   `CAMERA_GRAB_LATEST` + `fb_count=2`, `esp_camera_fb_get()` returns the most
   recent completed frame **immediately** — the camera keeps filling a fresh
   buffer even while the network is busy sending the previous one. This is the
   key stability fix: with the old `fb_count=1` + `GRAB_WHEN_EMPTY`, a slow TCP
   send held the only buffer and the camera dropped frames, collapsing FPS.
5. `esp_camera_fb_return()` frees the buffer back to the DMA pool.

## 4. How frames transfer over the network

The app runs **two** `esp_http_server` instances because one instance runs a
single select() loop per task — a forever-looping `/stream` handler would block
`/status` and `/control` (`app_httpd.c`).

| Server | Port | Routes |
|--------|------|--------|
| main   | 80   | `/`, `/favicon.ico`, `/capture`, `/status`, `/control`, `/classify` |
| stream | 81   | `/stream` (MJPEG only) |

`handler_stream()` loops for the lifetime of the connection:

```
fb = esp_camera_fb_get();                    // camera_task hands us a completed frame
   (optional detect: JPEG -> RGB565 -> classify -> draw boxes -> re-encode)
httpd_resp_send_chunk(part_header);          // Content-Type + Content-Length
httpd_resp_send_chunk(jpg_buf);              // the JPEG bytes
httpd_resp_send_chunk(boundary);             // multipart separator
esp_camera_fb_return(fb);
```

The response is **`multipart/x-mixed-replace`** MJPEG:

```
Content-Type: multipart/x-mixed-replace;boundary=123456789000000000000987654321

--123456789000000000000987654321
Content-Type: image/jpeg
Content-Length: 5213

<JPEG bytes>
--123456789000000000000987654321
...
```

Each JPEG frame is a separate multipart part, sent as HTTP chunked-transfer
chunks. There is no compression on the wire; bytes are whatever the sensor
encoded. QVGA JPEG frames are ~5 KB (~480 kbit/s at 22 FPS).

**Stall diagnostics** baked into the loop (`app_httpd.c`): per-second
`grab_max` (time in `fb_get`) vs `send_max` (time through the 3 chunk sends).
This is how the instability was traced to TCP TX stalls (big `send_max`, small
`grab_max`) rather than the sensor — fixed with `fb_count=2`/`GRAB_LATEST` plus
`esp_wifi_set_ps(WIFI_PS_NONE)` (modem-sleep power save used to wake the radio
and stall TX by hundreds of ms).

## 5. How the page renders frames — no Canvas, no WebGL/WebGPU

The web page (`g_index_html` in `app_httpd.c`) uses a **plain `<img>` element**:

```html
<img id="stream" src="http://<board-ip>:81/stream">
```

The browser natively decodes `multipart/x-mixed-replace` MJPEG and paints each
new JPEG part into the `<img>` as it arrives. **There is no HTML Canvas, no
WebGL, and no WebGPU** — no pixel decoding, no shaders, no per-frame JS
drawing. The browser's built-in JPEG decoder does all the work, which is why
the UI costs ~0 CPU.

Supporting pieces:

- **FPS readout**: JS polls `GET /status` every 1 s; the server computes FPS in
  `handler_stream` and returns `{"streaming":1,"fps":22.2,"w":320,"h":240,
  "format":4,"quality":12,"detect":0}`.
- **Controls**: `GET /control?res=...&quality=...&pixfmt=...&rot=...&detect=...`
  applies changes live; changing resolution/format calls `camera_reconfigure()`
  which deinit+reinit the camera (the DMA buffer is sized at init).
- **Detection overlay**: when "Draw boxes" is on, the *server* does the drawing
  (`stream_detect_frame`: JPEG->RGB565, classify, draw boxes, re-encode to
  JPEG). The browser still just renders JPEG frames — the overlay is baked into
  the picture, not a DOM/Canvas layer. QVGA drops to ~3.2 FPS in this mode
  because the CPU re-encodes every frame.
- **Static/`/capture`**: a single `GET /capture` returns one JPEG (direct
  `fb->buf` in JPEG mode, or `frame2jpg`-converted for RGB565).

If the stream were ever to move to Canvas/WebGL, that would only matter for
client-side overlays; the MJPEG `<img>` approach intentionally keeps the
browser trivial and pushes all CV work onto the ESP32.

## 6. End-to-end data flow (summary)

```
Sensor pixels (CMOS array)
  -> in-sensor JPEG encoder (SYSCLK 45/50 MHz)
  -> DVP parallel bus (8-bit, PCLK 11.25/10 MHz, VSYNC/HREF)
  -> ESP32-S3 LCD_CAM peripheral + GDMA ping-pong buffers
  -> cam_task assembles into PSRAM frame buffer (fb_count=2)
  -> esp_camera_fb_get() returns latest frame
  -> handler_stream writes multipart MJPEG chunks over TCP port 81
  -> lwIP -> WiFi radio (WIFI_PS_NONE) -> AP -> browser
  -> browser's native MJPEG decoder paints <img id="stream">
```

## 7. Why the two boards' FPS differs

Measured on the same AP, same firmware config (QVGA, quality 12):

| Board | SYSCLK | PCLK | QVGA FPS | max gap | ANT |
|-------|--------|------|----------|---------|-----|
| OV3660 | 50 MHz | 10 MHz | 27.7 | 70 ms | inserted |
| OV5640 | 45 MHz | 11.25 MHz | 22.2 | 90 ms | PCB |

Both are stall-free (0 gaps >300 ms). The OV3660 is faster because its JPEG
encoder runs at 50 MHz vs 45 MHz. The antenna difference (~2-3 dB) is
negligible at close range (both boards report RSSI -56 dBm) and only matters at
range/obstruction; it is not the cause of the OV5640's original instability.

## 8. IIC / SCCB control bus behavior

The video data rides the DVP parallel bus (§2.1), but the camera's *register*
interface — setting resolution, exposure, gain, PLL, etc. — is a 2-wire control
bus driven by the ESP32-S3's **hardware I2C peripheral**.

### 8.1 What SCCB is

SCCB (Serial Camera Control Bus) is OmniVision's camera-register protocol. It
is electrically identical to I2C (open-drain SDA + SCL, 7-bit device address +
R/W bit, ACK after each byte) but with one protocol difference that matters in
practice: the **read transaction shape** (see §8.3). The sensors here live at
address **0x3C** on the bus.

### 8.2 Hardware I2C, not bit-banged

With ESP-IDF v6.0.2, the esp32-camera component compiles `sccb-ng.c`
(`CMakeLists.txt:90-94` selects it when `idf_version >= 5.4` unless the legacy
driver is forced), which drives the SoC's **real I2C peripheral** through the
new IDF master-driver API:

```c
// sccb-ng.c:127 — new ESP-IDF I2C master API on the hardware peripheral
i2c_master_bus_config_t cfg = {
    .clk_source = I2C_CLK_SRC_DEFAULT,
    .i2c_port   = 1,                 // SCCB_I2C_PORT_DEFAULT
    .scl_io_num = 5, .sda_io_num = 4,
    .glitch_ignore_cnt = 7,
    .flags.enable_internal_pullup = 1,
};
i2c_new_master_bus(&cfg, &bus_handle);
```

Config on these boards (from `sdkconfig`): `CONFIG_SCCB_HARDWARE_I2C_DRIVER_NEW=y`,
`CONFIG_SCCB_HARDWARE_I2C_PORT1=y`, `CONFIG_SCCB_CLK_FREQ=100000` (100 kHz).
Boot log confirms: `sccb-ng: pin_sda 4 pin_scl 5`, `sccb-ng: sccb_i2c_port=1`.
There is **no software/bit-bang SCCB** in the modern component; the legacy
`sccb.c` also uses the hardware peripheral, just the older I2C API. Devices are
registered on the bus via `i2c_master_bus_add_device()` and every register
access goes through `i2c_master_transmit/receive` — pure hardware I2C.

### 8.3 The one SCCB quirk the hardware must handle: stop-between-read

| | Standard I2C read | Strict SCCB read |
|---|---|---|
| Sequence | SLA+W, reg, **repeated-START**, SLA+R, data | SLA+W, reg, **STOP**, SLA+R, data (new START) |
| Nature | one continuous transaction | two separate transactions |

SCCB's spec does *not* use a repeated-start: the address/register phase ends
with a STOP, then a fresh START begins the read phase. OmniVision's own
hardware often tolerates repeated-start, but some sensors reject it.

The ESP32-S3 I2C peripheral handles both, because a hardware "transaction"
can end with STOP and the next one can start with START. The driver exploits
this with a fallback in `SCCB_Read` (`sccb-ng.c:233-265`):

1. **Try repeated-start first** (fast, one transaction):
   `i2c_master_transmit_receive(dev, &reg, 1, &data, 1, ...)`
2. If the sensor rejects it, **fall back to strict SCCB** (STOP then new START):
   `i2c_master_transmit(dev, &reg, 1, ...)` followed by
   `i2c_master_receive(dev, &data, 1, ...)`

This is documented in the driver comment at `sccb-ng.c:240-245`. On these two
boards the OV5640/OV3660 accept the repeated-start path (sensors detect and
configure correctly at boot), so the fallback is rarely exercised — but it's
there for sensors that only honor the strict SCCB two-phase read.

### 8.4 Register access helpers

`sccb-ng.c` exposes both single- and double-width variants; the OV5640/OV3660
drivers use them to poke sensor registers:

| Function | Use |
|---|---|
| `SCCB_Write(addr, reg8, val)` | 8-bit register, 8-bit value (write only) |
| `SCCB_Read(addr, reg8)` | 8-bit register, 8-bit value (read; repeated-start + stop/start fallback) |
| `SCCB_Write16(addr, reg16, val)` | 16-bit register address, 8-bit value |
| `SCCB_Read16(addr, reg16)` | 16-bit register address, 8-bit value |
| `SCCB_Write_Addr16_Val16(addr, reg16, val16)` | 16-bit register, 16-bit value |
| `SCCB_Read_Addr16_Val16(addr, reg16)` | 16-bit register, 16-bit value |

Multi-byte payloads are sent as one `i2c_master_transmit` (no inter-byte
stops), and reads use the transmit_receive pattern of §8.3.

### 8.5 Why the bus can't be avoided

Even though the sensor JPEG-encodes in hardware, every capture parameter is
register-controlled: XCLK/PLL scaling (§2.3), frame size, exposure (AEC),
gain (AGC), white balance, flip/mirror, and JPEG quality. The camera is
configured *only* over this I2C/SCCB bus; the DVP pins carry pixels, never
registers. On boot the sensor is probed at 0x3C via `SCCB_Probe`, its PID read
(`0x5640` / `0x3660`), and the matching driver's `init()`/`set_pll()` write the
register tables through these helpers.
